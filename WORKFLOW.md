# WORKFLOW — как велась работа с AI

Документ отвечает на один вопрос: **что здесь сделал человек, а что AI, и как это проверить по репозиторию.**

Роль в проекте — frontend. Backend и AI-чат-бот делают другие участники; здесь их нет намеренно.

---

## Схема процесса

```
ai-rules/frontend_adilbek.md  →  план  →  этап  →  тесты  →  приёмка в браузере  →  коммит
        ↑                                                                                │
        └──────────────── правила уточняются, если этап их опроверг ─────────────────────┘
```

Порядок неслучаен. Спека роли писалась **первым коммитом**, до единой строки кода: она задаёт границы, запреты и контракты, на которые дальше опирается каждый этап. Документация, написанная после кода, описывает то, что получилось; написанная до — определяет, что должно получиться.

## Роль `ai-rules/frontend_adilbek.md`

Это не описание проекта, а рабочая инструкция агента. Из неё по ходу работы применялись, в частности:

| Правило из спеки | Как проявилось в коде |
|---|---|
| Данные — только через `frontend/src/api` | Правило `no-restricted-imports` в `frontend/eslint.config.js` физически запрещает импортировать адаптер из компонента |
| Прямой `fetch` вне адаптеров запрещён | Правило `no-restricted-globals`, отключённое только для `frontend/src/api/**` |
| `any` запрещён | `@typescript-eslint/no-explicit-any: error`, `strict: true`, `noUncheckedIndexedAccess` |
| Доменная логика не живёт в JSX | Цены и доступность вылетов вынесены в `frontend/src/domain/*` чистыми функциями |
| Фильтры — в URL, а не в состоянии React | `useTourFilters` работает поверх `useSearchParams` |
| Каждая фича приходит с тестом | 82 юнит- и компонентных теста + 14 E2E |
| Формат ответов: проверка фактической командой | Ни одно «готово» в истории не поставлено без прогона `typecheck / lint / test / build` |

## Журнал MCP и сабагентов

### Сабагент `general-purpose` — каталог туров

**Задача:** сгенерировать `frontend/src/mocks/tours.json` — 18 туров по 7 странам со связными описаниями, ценами, датами вылетов.

**Почему сабагент:** задача полностью изолирована (один файл, никакого общего состояния) и объёмна. Пока агент её выполнял, в основной сессии писался слой данных — работа шла параллельно.

**Что вернул:** 18 туров, 7 стран, 60 вылетов. Арифметика дат проверена скриптом по каждому вылету, включая переходы через границы месяцев и февраль 2027. Отдельно ценно: агент не поверил своей памяти насчёт ссылок на Unsplash, а прогнал каждый id через `curl -I` — два id оказались мёртвыми и в файл не попали.

**Оговорка, которую агент назвал сам:** проверено существование фотографий, но не их содержание. Тематическое соответствие картинки направлению — атрибуция, а не факт.

Эта оговорка оказалась важнее, чем выглядела. На приёмке выяснилось, что у тура по Тбилиси ведущим фото стоит Эйфелева башня, у Ари-Атолла — Сидней, Тадж-Махал и Колизей, а у Рас-эль-Хаймы с заголовком «эмират без небоскрёбов» — небоскрёбы и пицца. Агент честно предупредил о границах своей проверки; проигнорировать предупреждение было бы ошибкой человека, а не агента.

**Как чинилось.** Не наугад: сгенерирован контактный лист всех 54 изображений с подписями «тур → индекс кадра», просмотрен целиком, после чего кадры с чужими достопримечательностями удалены, а оставшиеся переназначены. Осталось 39 уникальных фото на 18 туров — повтор одного снимка в двух турах допущен сознательно: он честнее ложной подписи. Верно подобранное сохранено: у Стамбула — Голубая мечеть и Галатская башня, у Дубая — Бурдж-эль-Араб, у Мале — виллы на воде.

**Вывод для следующих задач:** «ссылка отвечает 200» и «на картинке то, что нужно» — разные утверждения. Первое проверяется скриптом, второе — только глазами.

### MCP `Claude_Browser` — визуальная приёмка

Ни один экран не считался готовым по факту «компилируется». Каждый проходил проверку в реальном браузере.

| Инструмент | Что дал |
|---|---|
| `preview_start` | Поднял dev-сервер. Порт 5173 оказался занят чужим процессом — это привело к правке: порт теперь читается из `PORT` |
| `navigate` + `get_page_text` | Проверка выдачи по прямой ссылке `?country=Грузия&sort=price-asc`: 2 тура, отсортированы по возрастанию цены |
| `read_page` | Дерево доступности. Здесь вскрылось, что категория отеля озвучивается как пять одинаковых звёзд независимо от реальной — исправлено отдельным коммитом |
| `form_input` + `computer` | Сквозное прохождение формы брони кликами и вводом |
| `read_console_messages` | Консоль на всех экранах чистая |
| `javascript_tool` | Диагностика: почему не сработал сабмит |
| `resize_window` | Проверка на 375×812 и 1280×900 |

**Отдельный случай, стоящий упоминания.** Клик по кнопке отправки через MCP не приводил к переходу. Прежде чем «чинить» форму, состояние было снято напрямую: значения полей, ошибки валидации, `localStorage`. Оказалось, что форма исправна, а клик не попадал по кнопке из-за высокого вьюпорта. Правки в коде не потребовалось — потребовалась проверка гипотезы. Обратный порядок (сначала правка, потом проверка) стоил бы вымышленного бага в рабочем коде.

### Скилл `code-review`

Прогон по итоговому диффу перед завершением работы. Нашёл четыре дефекта, каждый — с воспроизводимым сценарием, все исправлены отдельным коммитом:

1. **`TourImage` запоминал факт падения, а не упавший адрес.** В галерее один экземпляр компонента переиспользуется между кадрами, поэтому одна битая ссылка залипала заглушкой на всех последующих фото — до перезагрузки страницы.
2. **`departureId` из строки запроса не сверялся со списком вылетов.** Крафтом ссылки можно было оформить бронь на уже состоявшийся вылет: форма прятала его из списка, но значение поля оставалось, а адаптер искал вылет по полному списку. Проверка добавлена и в форму, и на границу слоя данных.
3. **Поля цены зеркалили строку запроса в собственное состояние.** При нажатии «назад» или сбросе фильтров в поле оставался фильтр, которого в выдаче уже нет. Правки-заплатки упирались в правила React (`set-state-in-effect`, затем `refs-during-render`) — это был сигнал, что дизайн неверен, а не что линтер придирается. Зеркало убрано целиком: поля неуправляемые, пересоздаются по `key`, значение уходит по Enter или потере фокуса. `useDebouncedValue` стал не нужен и удалён.
4. **Мок-адаптер хранил брони, но не списывал места.** Вылет с одним свободным местом бронировался дважды подряд — на демонстрации это выглядело бы как неработающая проверка. Каталог теперь отдаётся с учётом занятых мест, и то же поведение повторено в заглушке backend, иначе контрактный тест перестал бы что-либо доказывать.

Третий пункт стоит отдельного внимания как рабочий приём: когда линтер отвергает вторую попытку почини́ть симптом, дешевле пересмотреть решение, чем глушить правило.

## Что нашли тесты, а не глаза

Два дефекта в форме брони всплыли именно при написании тестов, а не на визуальной приёмке — оба зафиксированы отдельным коммитом `fix: итоговая сумма как <output>…`:

1. **Итоговая сумма была неотличима от промежуточной строки расчёта.** При двух гостях `200 000 × 2` и «Итого» давали одинаковый текст `400 000 ₸`. Тест не мог однозначно указать на итог — и пользователь скринридера тоже. Итог стал `<output>` с подписью: семантика вычисленного результата, роль `status`, значение озвучивается при пересчёте.
2. **Отказ сервера при создании брони всплывал необработанным промисом.** Сообщение в интерфейсе показывалось, но отклонение уходило в консоль. Погашено там, где обрабатывается.

## Переход на реальный API

Фронтенд начинался раньше бэкенда и работал на моках по собственной модели данных.
Когда появился контракт [`docs/superpowers/specs/api.md`](docs/superpowers/specs/api.md),
выяснилось, что модели расходятся принципиально: у тура одна пара дат вместо списка
вылетов, нет мест, рейтинга, звёзд, питания и галереи, идентификаторы целые,
страна приходит через `country_id`, ошибки имеют вид `{ error }` со статусом 422,
а сортировки в API нет вовсе.

**Что сделали и почему именно так:**

- **Мок-адаптер удалён.** Пока бэкенда не было, он давал работающий сайт; теперь
  вторая реализация того же контракта — это два источника правды и риск, что
  экраны отлажены на выдуманных данных. Осталась одна реализация — HTTP-клиент.
- **Из интерфейса убрано всё, чему нет опоры в API.** Сортировка, фильтр по числу
  гостей, выбор вылета, галерея, звёзды, питание, рейтинг, расчёт итоговой суммы
  и скидка за группу. Показывать их значило бы выдавать выдумку фронтенда за
  данные оператора — особенно сумму: сервер её не возвращает, а `price` не помечен
  как «за человека».
- **Дубликаты в каталоге оставлены как есть.** Один отель — это несколько туров
  с разными датами. Схлопывать их на клиенте можно только внутри загруженной
  страницы, то есть врать на границах пагинации.
- **snake_case заперт в одном файле.** Перевод в camelCase и проверка формы ответа
  делаются zod-схемами в `frontend/src/api/schemas.ts`. Дальше него `country_id`
  и `num_people` не проходят, а отступление бэкенда от контракта обнаруживается
  на границе слоя данных.
- **Заглушка бэкенда переехала в тесты.** `frontend/src/test/handlers.ts` повторяет
  спецификацию буква в букву и обслуживает и юнит-тесты (MSW в Node), и e2e
  (service worker в браузере). Сквозные сценарии по-прежнему не требуют поднятого
  Go-сервера с базой, но проверяют настоящий HTTP-клиент, а не мок-адаптер.

**Две ошибки по ходу, обе поучительные.**

Первая: многострочная запись файла через heredoc в bash молча не выполнилась —
скрипт упал на разборе кавычек, а bash разбирает команду целиком, поэтому
не выполнилось *ничего*, включая предыдущую запись. Файл остался старой версией,
которая продолжала компилироваться и проходить тесты, потому что все её зависимости
уцелели. Симптом всплыл только в браузере: в карточках вместо страны стоял прочерк.
Полчаса ушло на проверку гипотез про React Compiler и кэш react-query, прежде чем
выяснилось, что дело в невыполненной записи. Вывод: после пакетной записи файлов
проверять результат, а не только код возврата последней команды.

Вторая: e2e-тест на страну проходил ложно. В Playwright строковый `getByText`
ищет подстроку, а названия туров по ОАЭ начинаются с «ОАЭ:» — совпадал заголовок,
а не подпись страны. Ошибка маскировала настоящий баг ровно до тех пор, пока
такой же тест не написали для Турции, где заголовок начинается со «Стамбул».
С тех пор в спеках, где важна точная подпись, стоит `{ exact: true }`.

## Как читать историю git

История разбита по этапам, каждый коммит — законченный кусок с зелёными проверками:

```
docs:  спецификация frontend-роли        ← правила, до кода
chore: каркас Vite + React + TS + Tailwind
feat(api): слой данных mock/backend
feat(ui): каталог, страница тура, бронирование
fix:   доступность звёзд, порт dev-сервера
fix:   итоговая сумма и отказ формы      ← найдено тестами
test:  контрактные и компонентные тесты
test:  сквозные сценарии Playwright
fix(ui):   изображение заполняет рамку   ← найдено на скриншотах
fix(data): изображения соответствуют направлениям
docs:  README и WORKFLOW
fix:   правки по код-ревью
chore: приложение переехало в frontend/
feat(api): фронтенд переведён на реальный контракт бэкенда
```

Порядок читается как ход работы: сначала правила, потом код, потом проверки — и три волны исправлений, каждая от своего способа проверки. Тесты, скриншоты и ревью нашли разные дефекты; ни один из трёх не заменяет двух других.

Авторство AI видно в каждом коммите — трейлер `Co-Authored-By: Claude`:

```bash
git log --format='%h %s%n%b' | grep -c 'Co-Authored-By: Claude'
```

## Соблюдение anti-patterns

| Правило | Как соблюдено |
|---|---|
| Не переписывать AI-код руками | Все правки внесены агентом через инструменты редактирования. Ручных коммитов в истории нет |
| Следы AI в git | Трейлер `Co-Authored-By` в каждом коммите; этапность истории отражает ход работы |
| Не «один AI на всё» | Каталог отдан отдельному сабагенту; ревью — отдельному скиллу; основная сессия вела архитектуру и код |
| Не «GPT-чат без tools» | Работа шла через инструменты: файловые правки, запуск проверок, браузерный MCP. Ни одного «вот тебе код, вставь сам» |

## Что дальше

1. **Подключение реального backend.** Правится `.env`, не код: `VITE_API_MODE=http` и `VITE_API_BASE_URL`. Контракт эндпоинтов описан в `ai-rules/frontend_adilbek.md` → Output Contracts → HTTP. Совместимость страхует `frontend/src/api/__tests__/contract.test.ts` — он гоняет один набор проверок по обоим адаптерам.
2. **AI-чат-бот.** В текущей итерации не делался осознанно. Слой `frontend/src/api` — готовая площадка для его инструментов: `listTours` уже принимает бюджет, даты и число гостей, то есть подбор тура ботом сводится к вызову существующего контракта, а не к новому коду.

# Backend

Роль в проекте — backend. Код в `backend/` (Go + Echo + PostgreSQL), схема БД и сид-данные — там же, корневой `docker-compose.yml` сшивает backend с frontend и ai-service.

## Схема процесса

```
brainstorming (спек-ревью)  →  docs/superpowers/specs/2026-08-20-tours-backend-design.md
        →  миграции + sqlc-запросы  →  handler/service/repository  →  тесты  →  curl-приёмка  →  коммит
```

В отличие от frontend, спека здесь не была отдельным ai-rules-файлом с первого коммита: сначала прошёл полный цикл `brainstorming` (вопросы → варианты архитектуры → design doc, закоммичен в `docs/superpowers/specs/2026-08-20-tours-backend-design.md`), и только после явного «да, устраивает» началась реализация. `ai-rules/backend_rustem.md` написан по итогам, как рабочая инструкция на будущее, а не как ТЗ, которое читалось перед первой строкой кода — это осознанное отступление от схемы frontend-роли, а не забытый шаг.

## Роль `ai-rules/backend_rustem.md`

| Правило из спеки | Как проявилось в коде |
|---|---|
| Слои `handler → service → repository`, бизнес-логика — в `service` | `internal/handler/*` только парсит query/body и сериализует ответ; вся валидация и обращения к БД — в `internal/service/*` |
| SQL руками, генерация — через sqlc | `internal/db/queries/*.sql` пишутся вручную, `internal/repository/*.sql.go` — `// Code generated by sqlc. DO NOT EDIT.`, руками не редактировались |
| Единый формат ошибок `{"error": "..."}` | `apperror.NotFound` / `apperror.Validation` + один `echo.HTTPErrorHandler` на всё приложение — ни одного хендлера с собственным форматом ошибки |
| Не расширять скоуп без запроса (auth, admin CRUD, проверка вместимости) | Все три пункта явно зафиксированы как «вне скоупа» в design doc после прямых вопросов пользователю, а не решены молча по ходу кода |
| Каждое изменение схемы — новый файл миграции | Единственная миграция `0001_init_schema.{up,down}.sql`, `.down.sql` написан вместе с `.up.sql`, а не постфактum |
| Перед «готово» — гонять тесты, не только `go build` | Ни один этап не считался законченным без `go build ./... && go test ./...` (юнит) и отдельно интеграционных с поднятой `tours_test` |

## Журнал MCP и сабагентов

### Playwright MCP — сквозная проверка живого стека

MCP использовался не во время написания Go-кода (там основной инструмент — `go test` и `curl`), а там, где `curl` недостаточно: чтобы увидеть то же, что видит пользователь в браузере.

**Кейс 1 — «не вижу фронта».** Пользователь поднял `docker compose` и сообщил, что фронтенд не открывается. Вместо гадания: `browser_navigate` на `localhost:5173`, `browser_console_messages` на наличие JS-ошибок. Страница отдавала корректный HTML/JS/CSS (проверено и `curl`, и в реальном браузере) — на момент проверки ошибок не воспроизвелось, MCP дал точный ответ «сервер отвечает правильно», а не косвенный вывод по кодам HTTP.

**Кейс 2 — кракозябры в Safari.** Пользователь сообщил про `ÐžÐ` при открытии `/api/v1/countries` в Safari. Байты на выходе бэкенда проверены через `curl | xxd` — корректный UTF-8. Причина — Safari не считает `application/json` без `charset` автоматически UTF-8 (в отличие от Chrome). Это нашёл не тест и не MCP, а прямой репорт пользователя из реального браузера; после диагностики через `curl -sD -` (заголовки ответа) добавлена `jsonCharsetMiddleware` в `internal/app/app.go`, проверено пересборкой образа и повторным `curl`.

### Отдельный агент для скрейпа требований

Требования проекта лежали на закрытой Notion-странице. Playwright MCP использован для навигации и снятия accessibility snapshot страницы, результат вручную структурирован в `requirement.md` — без агента пришлось бы копировать текст руками из рендера Notion.

## Что нашли curl/тесты, а не глаза — и наоборот

В отличие от frontend, где расхождения ловили тесты и скриншоты, на backend основных находки было две, и обе — от прямого прогона, а не от чтения кода:

1. **Опечатка в generated SQL не всплыла бы без прогона.** При генерации `seed.sql` из сырых данных (`tour_platform.sql`) в одном `format(...)`-запросе была допущена именованная нотация вместо позиционной (`departure_date := ...`) — Postgres сразу вернул `ERROR: positional argument cannot follow named argument`. Ошибка синтаксическая, не логическая: `go vet`/тесты её бы не поймали, поймал только реальный прогон запроса против БД.
2. **`Content-Type` без `charset` — валиден по RFC 8259, но ломает Safari.** Ни один backend-тест (юнит или интеграционный, через `httptest`) не проверяет рендеринг в конкретном браузере — такой класс багов тестами на этом уровне принципиально не ловится, только ручной или browser-MCP приёмкой.

## Данные: не просто сид, а трансформация чужой схемы

Отдельная часть работы, которой нет аналога во frontend-журнале: сырые скрейпленные данные (`tour_platform.sql`) пришли в **другой**, куда более богатой схеме (13 таблиц: `country → destination → hotel → tour_package → tour_offer`, с `hotel_image`, `amenity` и т.д.), чем наша (`countries`/`tours`/`bookings`, 3 таблицы). Загрузка «как есть» была невозможна.

Решение: сырой файл поднят во временную БД (`tour_platform_raw`), одним SQL-запросом с `format()` и `row_number()` сгенерированы `INSERT`-инструкции под нашу схему (маппинг `destination_type` → `category`, сборка `description` из нескольких исходных полей, выбор только `is_active = TRUE` офферов — 48 из 60), результат сохранён как воспроизводимый `backend/internal/db/seed/seed.sql`, временная БД удалена. Числа проверены против явных sanity-check комментариев в исходном файле (`Must return 12 packages`, `Must return 48 active future demo offers`) — совпали.

## Кросс-сервисная фича: ссылки на туры в чате

Пользователь заметил, что AI-помощник называет туры, но не даёт на них ссылку. Задача с самого начала пересекала границу двух ролей — backend/ai-service и frontend, — и обсуждалась как единый дизайн, а не как два независимых тикета:

1. **ai-service.** `mcp_server.py` при сериализации тура для инструментов (`search_tours`/`get_tour_details`/`compare_tours`) добавляет поле `url` = `FRONTEND_URL + /tours/{id}` — новая настройка в `config.py`, дефолт `http://localhost:5173`. Промпт агента (`agent.py`) явно требует приводить это поле как есть и никогда не составлять ссылку самому — источник правды один, не память модели.
2. **frontend.** `ChatBubble.tsx` до этой правки рендерил ответ агента как голый `<p>{text}</p>` — ссылка, даже если бы пришла, осталась бы невидимой строкой. Добавлен `src/lib/linkify.tsx`: разбирает текст на фрагменты и оборачивает URL в `<a target="_blank">`.

**Промежуточный баг, который нашёл не тест, а пользователь.** Первая версия `linkify` формально была ссылкой (`<a>` + `underline`), но красилась в цвет окружающего текста, а подписью служил сырой URL целиком — визуально неотличимо от обычного текста. Ни один assert на `href`/`role="link"` в `linkify.test.tsx` этого не поймал — тест проверял, что это ссылка, а не то, что она выглядит как ссылка. Починено после прямого репорта («показывает голые url»): подпись `Смотреть тур →` для распознанных `/tours/:id`-ссылок и цвет `text-brand-700`, тот же токен, что уже используют `TourCard`/`TourDetailsPage`/`BookingPage`. Разметку проверили не на глаз, а вытащили `container.innerHTML` из рендер-теста и прочитали как текст — тот же принцип, что и в кейсе с Safari-кракозябрами: не верить, что «похоже на правильное», а посмотреть на фактический результат.

**Гонка с параллельным коммитом.** Пока эта фича писалась, в `origin/master` прилетел чужой коммит (`fix ai rules`, автор — AI Engineer), правивший тот же `SYSTEM_PROMPT` в `agent.py` — добавлял guardrails против непрофильных запросов. `git rebase origin/master` дал конфликт ровно в этом месте. Разрешено вручную: оба намерения сохранены (guardrails идут первым блоком, инструкция про `url` — вторым), после чего `agent.py` пересобран в Docker и прогнан весь набор из 21 теста ai-service заново — это не формальность, слияние текста промпта руками легко могло случайно потерять кусок смысла одной из сторон.

## Как читать историю git

```
docs:  design doc backend-роли, закоммичен и одобрен до кода
feat:  backend на Go + Echo + PostgreSQL (handler/service/repository, sqlc, миграции, seed из сырых данных, тесты, Dockerfile)
docs:  детальный контракт API (backend/api.md)
feat(chat): ai-service отдаёт url тура, frontend рендерит кликабельную ссылку
fix(chat): читаемая подпись и цвет ссылки вместо голого URL
```

Авторство AI видно так же, как и во frontend-истории — трейлером `Co-Authored-By: Claude` в коммитах, созданных через `git commit`.

## Соблюдение anti-patterns

| Правило | Как соблюдено |
|---|---|
| Не переписывать AI-код руками | Все правки — через Edit/Write, включая правку опечатки в SQL-генераторе seed'а |
| Следы AI в git | `Co-Authored-By: Claude` в бэкенд-коммитах |
| Не «один AI на всё» | Playwright MCP — отдельно для браузерной приёмки, `go test`/`curl` — для контрактной |
| Не «GPT-чат без tools» | Вся работа — через файловые правки, `go build`/`go test`, `docker`/`psql` в реальном окружении, ни разу «вот код, вставь сам» |
| Сайт работает без AI | Backend не содержит AI-логики вообще: чат-бот — отдельный сервис (`ai-service`), backend отдаёт данные любому потребителю, включая обычный `curl` |

# Team Reflection

1. **Где AI сэкономил больше всего времени?**
   Генерация слоя `repository` через sqlc из написанных вручную SQL-запросов, и особенно — трансформация 48 строк реальных scraped-данных из чужой 13-табличной схемы в свою тремя SQL-запросами с `format()`/`row_number()` вместо ручного переноса значений. Вручную это была бы full-time задача на десятки повторяющихся `INSERT`, а не работа одной сессии.

2. **Где AI ошибался?**
   Трижды, и все три — один и тот же класс ошибки: формальная проверка проходила, а фактический результат был неверен. Опечатка (`:=` вместо `,`) в SQL-генераторе seed-данных — поймана сразу по ошибке Postgres, не дошла до коммита; отсутствие `charset=UTF-8` в JSON-ответах — валидно по HTTP-спеке, но ломало Safari, всплыло только по отчёту пользователя; первая версия ссылки на тур в чате технически была `<a href>` и проходила assert на `role="link"`, но выглядела как обычный текст — тест проверял факт наличия ссылки, а не то, что пользователь способен её заметить. Вывод одинаковый во всех трёх: «тест зелёный» и «результат корректен» — разные утверждения, если тест не смотрит именно туда, где кроется расхождение.

3. **Что без AI заняло бы ×3 времени?**
   Стыковка между тремя независимо написанными сервисами (backend/frontend/ai-service) без единого API-контракта на старте: сверка `internal/dto/dto.go` ↔ `frontend/src/api/schemas.ts` ↔ `ai-service/app/schemas.py` поле за полем заняла минуты благодаря возможности читать и сопоставлять код всех трёх репозиториев параллельно в одной сессии, а не за счёт документации, которую пришлось бы писать и поддерживать вручную по мере расхождений.
