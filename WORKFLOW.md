# WORKFLOW — как велась работа с AI

Документ отвечает на один вопрос: **что здесь сделал человек, а что AI, и как это проверить по репозиторию.**

Роль в проекте — frontend. Backend и AI-чат-бот делают другие участники; здесь их нет намеренно.

---

## Схема процесса

```
ai-rules/frontend.md  →  план  →  этап  →  тесты  →  приёмка в браузере  →  коммит
        ↑                                                                      │
        └──────────────── правила уточняются, если этап их опроверг ───────────┘
```

Порядок неслучаен. Спека роли писалась **первым коммитом**, до единой строки кода: она задаёт границы, запреты и контракты, на которые дальше опирается каждый этап. Документация, написанная после кода, описывает то, что получилось; написанная до — определяет, что должно получиться.

## Роль `ai-rules/frontend.md`

Это не описание проекта, а рабочая инструкция агента. Из неё по ходу работы применялись, в частности:

| Правило из спеки | Как проявилось в коде |
|---|---|
| Данные — только через `src/api` | Правило `no-restricted-imports` в `eslint.config.js` физически запрещает импортировать адаптер из компонента |
| Прямой `fetch` вне адаптеров запрещён | Правило `no-restricted-globals`, отключённое только для `src/api/**` |
| `any` запрещён | `@typescript-eslint/no-explicit-any: error`, `strict: true`, `noUncheckedIndexedAccess` |
| Доменная логика не живёт в JSX | Цены и доступность вылетов вынесены в `src/domain/*` чистыми функциями |
| Фильтры — в URL, а не в состоянии React | `useTourFilters` работает поверх `useSearchParams` |
| Каждая фича приходит с тестом | 126 юнит- и компонентных тестов + E2E |
| Формат ответов: проверка фактической командой | Ни одно «готово» в истории не поставлено без прогона `typecheck / lint / test / build` |

## Журнал MCP и сабагентов

### Сабагент `general-purpose` — каталог туров

**Задача:** сгенерировать `src/mocks/tours.json` — 18 туров по 7 странам со связными описаниями, ценами, датами вылетов.

**Почему сабагент:** задача полностью изолирована (один файл, никакого общего состояния) и объёмна. Пока агент её выполнял, в основной сессии писался слой данных — работа шла параллельно.

**Что вернул:** 18 туров, 7 стран, 60 вылетов. Арифметика дат проверена скриптом по каждому вылету, включая переходы через границы месяцев и февраль 2027. Отдельно ценно: агент не поверил своей памяти насчёт ссылок на Unsplash, а прогнал каждый id через `curl -I` — два id оказались мёртвыми и в файл не попали.

**Оговорка, которую агент назвал сам:** проверено существование фотографий, но не их содержание. Тематическое соответствие картинки направлению — атрибуция, а не факт.

Эта оговорка оказалась важнее, чем выглядела. На приёмке выяснилось, что у тура по Тбилиси ведущим фото стоит Эйфелева башня, у Ари-Атолла — Сидней, Тадж-Махал и Колизей, а у Рас-эль-Хаймы с заголовком «эмират без небоскрёбов» — небоскрёбы и пицца. Агент честно предупредил о границах своей проверки; проигнорировать предупреждение было бы ошибкой человека, а не агента.

**Как чинилось.** Не наугад: сгенерирован контактный лист всех 54 изображений с подписями «тур → индекс кадра», просмотрен целиком, после чего кадры с чужими достопримечательностями удалены, а оставшиеся переназначены. Осталось 39 уникальных фото на 18 туров — повтор одного снимка в двух турах допущен сознательно: он честнее ложной подписи. Верно подобранное сохранено: у Стамбула — Голубая мечеть и Галатская башня, у Дубая — Бурдж-эль-Араб, у Мале — виллы на воде.

**Вывод для следующих задач:** «ссылка отвечает 200» и «на картинке то, что нужно» — разные утверждения. Первое проверяется скриптом, второе — только глазами.

### MCP `Claude_Browser` — визуальная приёмка

Ни один экран не считался готовым по факту «компилируется». Каждый проходил проверку в реальном браузере.

| Инструмент | Что дал |
|---|---|
| `preview_start` | Поднял dev-сервер. Порт 5173 оказался занят чужим процессом — это привело к правке: порт теперь читается из `PORT` |
| `navigate` + `get_page_text` | Проверка выдачи по прямой ссылке `?country=Грузия&sort=price-asc`: 2 тура, отсортированы по возрастанию цены |
| `read_page` | Дерево доступности. Здесь вскрылось, что категория отеля озвучивается как пять одинаковых звёзд независимо от реальной — исправлено отдельным коммитом |
| `form_input` + `computer` | Сквозное прохождение формы брони кликами и вводом |
| `read_console_messages` | Консоль на всех экранах чистая |
| `javascript_tool` | Диагностика: почему не сработал сабмит |
| `resize_window` | Проверка на 375×812 и 1280×900 |

**Отдельный случай, стоящий упоминания.** Клик по кнопке отправки через MCP не приводил к переходу. Прежде чем «чинить» форму, состояние было снято напрямую: значения полей, ошибки валидации, `localStorage`. Оказалось, что форма исправна, а клик не попадал по кнопке из-за высокого вьюпорта. Правки в коде не потребовалось — потребовалась проверка гипотезы. Обратный порядок (сначала правка, потом проверка) стоил бы вымышленного бага в рабочем коде.

### Скилл `code-review`

Прогон по итоговому диффу перед завершением работы.

## Что нашли тесты, а не глаза

Два дефекта в форме брони всплыли именно при написании тестов, а не на визуальной приёмке — оба зафиксированы отдельным коммитом `fix: итоговая сумма как <output>…`:

1. **Итоговая сумма была неотличима от промежуточной строки расчёта.** При двух гостях `200 000 × 2` и «Итого» давали одинаковый текст `400 000 ₸`. Тест не мог однозначно указать на итог — и пользователь скринридера тоже. Итог стал `<output>` с подписью: семантика вычисленного результата, роль `status`, значение озвучивается при пересчёте.
2. **Отказ сервера при создании брони всплывал необработанным промисом.** Сообщение в интерфейсе показывалось, но отклонение уходило в консоль. Погашено там, где обрабатывается.

## Как читать историю git

История разбита по этапам, каждый коммит — законченный кусок с зелёными проверками:

```
docs:  спецификация frontend-роли        ← правила, до кода
chore: каркас Vite + React + TS + Tailwind
feat(api): слой данных mock/backend
feat(ui): каталог, страница тура, бронирование
fix:   доступность звёзд, порт dev-сервера
fix:   итоговая сумма и отказ формы
test:  контрактные и компонентные тесты
test:  сквозные сценарии Playwright
docs:  README и WORKFLOW
```

Авторство AI видно в каждом коммите — трейлер `Co-Authored-By: Claude`:

```bash
git log --format='%h %s%n%b' | grep -c 'Co-Authored-By: Claude'
```

## Соблюдение anti-patterns

| Правило | Как соблюдено |
|---|---|
| Не переписывать AI-код руками | Все правки внесены агентом через инструменты редактирования. Ручных коммитов в истории нет |
| Следы AI в git | Трейлер `Co-Authored-By` в каждом коммите; этапность истории отражает ход работы |
| Не «один AI на всё» | Каталог отдан отдельному сабагенту; ревью — отдельному скиллу; основная сессия вела архитектуру и код |
| Не «GPT-чат без tools» | Работа шла через инструменты: файловые правки, запуск проверок, браузерный MCP. Ни одного «вот тебе код, вставь сам» |
| Коммиты после 20:30 | Первые пять коммитов уложились в окно. Дальнейшие сделаны позже — сознательное решение владельца проекта, принятое после того, как ограничение было названо явно |

## Что дальше

1. **Подключение реального backend.** Правится `.env`, не код: `VITE_API_MODE=http` и `VITE_API_BASE_URL`. Контракт эндпоинтов описан в `ai-rules/frontend.md` → Output Contracts → HTTP. Совместимость страхует `src/api/__tests__/contract.test.ts` — он гоняет один набор проверок по обоим адаптерам.
2. **AI-чат-бот.** В текущей итерации не делался осознанно. Слой `src/api` — готовая площадка для его инструментов: `listTours` уже принимает бюджет, даты и число гостей, то есть подбор тура ботом сводится к вызову существующего контракта, а не к новому коду.
