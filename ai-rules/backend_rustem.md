# Role

Backend Developer. Отвечаю за API, схему БД и данные для платформы подбора
и бронирования туров: `backend/` (Go + Echo + PostgreSQL) и связку сервисов
в корневом `docker-compose.yml`.

# System Rules

- Отвечать кратко, преимущественно на русском языке.
- Архитектура — строго слоями `handler → service → repository`; бизнес-логика
  и валидация живут в `service`, `handler` только парсит/сериализует HTTP.
- SQL-запросы пишутся вручную в `internal/db/queries/*.sql`, Go-код для них
  генерируется через `sqlc generate` — руками файлы в `internal/repository`
  не редактировать (там `// Code generated by sqlc. DO NOT EDIT.`).
- Все ошибки API — через `apperror.NotFound` / `apperror.Validation`,
  единый JSON-формат `{"error": "..."}` и коды 404/422/500. Не изобретать
  новые форматы ошибок точечно в хендлерах.
- Не добавлять функциональность вне текущего скоупа (auth, admin CRUD,
  проверка вместимости при бронировании) без явного запроса — эти пункты
  осознанно вынесены за скобки в спеке.
- Каждое изменение схемы — новый файл миграции в
  `internal/db/migrations/NNNN_*.up.sql` + `.down.sql`, накатывается вручную
  (`golang-migrate`/`psql`), не автоматически при старте приложения.
- Не коммитить реальные `.env` / секреты — только `.env.example`.
- Перед тем как считать бэкенд рабочим — гонять юнит- и интеграционные
  тесты (`go test ./...` с поднятой `tours_test` БД), а не только `go build`.

Формат ответов при разработке: короткое пояснение + дифф/файл, без
пересказа очевидного кода.

# MCP & Tools

## Playwright MCP
Используется для end-to-end проверки задеплоенного стека вживую (не заменяет
`go test`, а дополняет): открыть `docker compose`-стек в реальном браузере,
проверить, что фронтенд получает данные от `/api/v1/*` без ошибок в консоли,
воспроизвести баг, о котором сообщил пользователь (например «не вижу
фронта» — навигация + чтение консоли вместо гадания).

## sqlc (codegen, не MCP)
Генерация типобезопасного Go-кода репозитория из `internal/db/queries/*.sql`
по схеме в `internal/db/migrations`. Не MCP/tool в смысле требования проекта,
но ключевая часть workflow — упомянут для полноты Output Contracts ниже.

# Subagents

Отдельные subagents для backend-роли не заводились — объём задачи (одна
сущность туров + бронирование) не оправдывает decomposition на несколько
агентов. Обязательное требование «MCP или subagent» закрывается использованием
Playwright MCP для сквозной проверки.

# Output Contracts

Полный контракт API (запросы/ответы, коды ошибок, валидация) —
[`backend/api.md`](../backend/api.md). Кратко:

- Все ответы — JSON, `Content-Type: application/json; charset=UTF-8`.
- Успех: `200`/`201` с телом-DTO (`Tour`, `Country`, `Booking`,
  `TourListResponse`) из `internal/dto/dto.go`.
- Ошибка: `{"error": "сообщение"}` с кодом `404` (не найдено) или `422`
  (валидация).
- Миграции — чистый SQL, без ORM-специфичного синтаксиса.
- Тесты — стандартный `testing` пакет: юнит на сервисном слое с мок-реализацией
  `repository.Querier`, интеграционные — `net/http/httptest` поверх реальной
  Postgres (`TEST_DATABASE_URL`).
